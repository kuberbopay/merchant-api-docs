Merchant API

Accept payments with the KuberoPay API

A merchant-facing guide to taking a payment end to end: create an API key, generate a payment link, check its status, and receive webhooks. Everything you need to wire KuberoPay into your own checkout.

Production https://api.kuberopay.com/api/v1 live
UAT / sandbox https://uatapi.kuberopay.com/api/v1 test

Overview

Three calls take you from nothing to a paid order. Create a payment link, hand the returned checkout URL to your customer, and confirm the outcome by webhook or by polling the link.

01

Create an API key

Issue a secret key in the console, once, under Developers.

02

Create a payment link

POST the amount and customer. Get back a hosted checkout URL.

03

Confirm the result

Receive a signed webhook, or poll the link for its status.

Create your API key

API keys are issued from the KuberoPay merchant console, not from the API itself. You need a team member with the Merchant admin role.

Steps

1Open the console for the environment you want, on the API keys page (menu: Developers → API keys):
Test: https://uatapp.kuberopay.com/api/keys
Live: https://app.kuberopay.com/api/keys
2Select Issue key. You do not pick the mode - the UAT console mints sk_test_ keys, the live console mints sk_live_ keys.
3Copy the secret from the dialog into your server-side secret manager. It is shown once and cannot be retrieved later.
4Yes, you create a key per environment. Make a test key in UAT while you build, then a separate live key in the live console before going live. Keys never carry between environments.
5If a key is ever exposed, revoke it on the same screen and issue a new one.
!

Keep secret keys server-side. A key starting sk_ can move money. Never ship it in browser, mobile, or any client-side code, and never commit it to a repository.

Authentication

Every request to /api/v1 is authenticated with your secret key as a Bearer token over HTTPS.

Scopes

A key carries scopes that limit what it can do. A newly issued key gets payment:read, payment:write, and refund:write. Payout scopes are granted separately.

Idempotency

Send an Idempotency-Key header on every money-moving POST (payment intents, refunds, payouts). Retrying the same key returns the original result instead of creating a duplicate, so a network timeout never charges twice.

Request signing

Money mutations - confirming an intent, creating a refund or a payout - must also be signed with an X-KP-Signature header so a leaked read of your traffic cannot be replayed. Read requests need only the Bearer key.

i

The signature is valid for 5 minutes. This inbound scheme (you → KuberoPay, keyed with your API key) is different from the outbound webhook signature described under Webhooks (KuberoPay → you, keyed with a per-endpoint secret). Do not mix them up.

Create a payment link

A payment link is the simplest way to take a payment. Post the amount and the customer, and receive a hosted checkout URL you hand to the buyer. This is your order-creation call.

POST /payment_links requires payment:write

Request body

FieldTypeNotes
amount requiredstringDecimal amount, e.g. "499.00". Uses the currency's own scale.
currency requiredstringISO code, e.g. "INR", "USD", "EUR".
customer requiredobject{ name, email, phone } - all three required.
descriptionstringShown to the buyer on the checkout page.
reference_idstringYour own order id. Echoed back and searchable.
expires_atstringISO time after which the link cannot be paid.
allowed_methodsstring[]Restrict methods, e.g. ["card","upi","crypto"]. Omit to allow all enabled methods.
successobject{ redirect_url, message } - where to send the buyer after paying.
metadataobjectAny key/value pairs you want returned with the link.

Response

Send the buyer to url. KuberoPay hosts the checkout, presents the enabled methods (card, UPI, or crypto), and collects the payment.

Check payment status

Retrieve a link to see whether it has been paid. The response embeds the linked payment and its lifecycle status.

GET /payment_links/{id} requires payment:read
i

Polling is fine for low volume, but webhooks are the recommended way to learn the moment a payment succeeds - especially for crypto, where confirmation takes minutes.

List payments

Page through your links, filter by status or date, or search for one by id.

GET /payment_links requires payment:read
QueryNotes
page, pageSizePagination. The response returns page, pageSize, and total.
statusComma-separated, e.g. active,paid.
currencyFilter to one currency.
created_from, created_toISO time range.
qSearch by id or reference.

Refund a payment

Refund a captured payment in full or in part. A refund enters review and settles once approved, so its status starts at pending.

POST /refunds requires refund:write · signed · idempotent

Webhooks

A webhook is how KuberoPay tells your server the moment a payment changes - the reliable way to learn an outcome without polling. You register one endpoint URL per environment in the console; KuberoPay then POSTs a signed event to it on every payment change.

Set it up (once per environment)

1Open Developers → Webhooks in the console:
Test: https://uatapp.kuberopay.com/api/webhooks
Live: https://app.kuberopay.com/api/webhooks
2Select Add endpoint and enter your own HTTPS URL that will receive events, e.g. https://yourshop.com/webhooks/kuberopay.
3Choose which events to receive, or keep the default set (it already includes the payment events). Save.
4Copy the signing secret shown for the endpoint - you use it to verify every delivery (below). It is shown once; you can rotate it later from the same screen.
5Use Send test event to fire a sample delivery and confirm your endpoint replies 2xx.

What a delivery looks like

Verify the signature

Each delivery carries x-kp-signature (a hex HMAC of the raw body, keyed with your endpoint's signing secret) and x-kp-event-id for de-duplication. Compute the same HMAC over the raw request body and compare in constant time before trusting the event. Delivery is at-least-once, so treat repeated x-kp-event-id values as one.

Crypto deposit status

When a buyer pays with crypto, the payment moves through these on-chain states, surfaced via the crypto.payment.* webhooks.

Test vs Live

KuberoPay runs two separate environments on two hosts. Build and test against UAT at uatapi.kuberopay.com with a sk_test_ key (no real money, crypto on testnet), then move to Production at api.kuberopay.com with a sk_live_ key for real transactions. Each environment issues its own keys, so a test key never reaches production.

UAT / sandboxProduction
Base URLhttps://uatapi.kuberopay.com/api/v1https://api.kuberopay.com/api/v1
Key prefixsk_test_…sk_live_…
MoneyNo real funds; testnet for cryptoReal funds; mainnet for crypto

Errors

Errors return a standard problem document with an HTTP status and a machine-readable code. Read the code, not the message text, when branching in your integration.

HTTPWhenWhat to do
401Missing, wrong, or wrong-mode key.Check the Bearer key and that its mode matches your environment.
403merchant_not_approved, or a scope the key lacks.Complete onboarding, or issue a key with the needed scope.
409An Idempotency-Key was reused with a different body.Use a fresh key for a new request.
422Validation failed on a field.Fix the field named in the response and retry.
429Rate limited.Back off and retry after the indicated window.
